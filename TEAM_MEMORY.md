# Общая память агентов команды

Этот протокол действует для агентов участников проекта `GalimovKI/pentada-astr`. Задача — обмениваться результатами разработки и экспериментов до слияния кода. Агент выполняет подключение, чтение и публикацию самостоятельно в рамках своей задачи. Отдельный сервис или скрипт для первой версии не требуется.

Правила поведения находятся в [AGENTS.md](AGENTS.md), правила оценки — в [EVAL.md](EVAL.md). Общая память хранит сведения и доказательства; изменения общих правил и архитектуры оформляются в основных документах проекта.

## 1. Где находятся знания

- `origin/main` — код и согласованные инструкции: AGENTS.md, PROJECT.md, DATA.md, COMPONENTS.md, EVAL.md и этот протокол.
- `origin/team-memory` — отдельная ветка только для журнала. Она не требует слияния экспериментального кода и не сливается целиком в `main`.
- Ветка задачи участника — исходники эксперимента и конфигурации, доступные по коммиту.

Структура ветки журнала:

```text
README.md
experiments/<id>/
    record.json
    summary.md
    run.json          # Когда прогон уже состоялся; исходный файл eval
    metrics.json      # Когда eval сформировал метрики; исходный файл
findings/<id>/
    record.json
    summary.md
```

Каждая запись имеет своего владельца. Индекс записей получается просмотром дерева и поиском по файлам; общий дописываемый файл со всеми результатами не нужен. Так независимые публикации затрагивают разные пути.

## 2. Подключение и чтение перед работой

1. Определи корень checkout и рабочую ветку, проверь локальные изменения. Пользовательскую работу сохраняй.
2. Проверь `origin`: он должен указывать на командный репозиторий `GalimovKI/pentada-astr` через доступный участнику SSH или HTTPS URL. Используй существующую авторизацию Git.
3. Выполни `git fetch origin`. Прочитай инструкции из текущего checkout; при первом подключении или обновлении протокола проверь также версии AGENTS.md и TEAM_MEMORY.md в `origin/main`.
4. Убедись в наличии журнала. Если ветки нет, используй раздел 3; ошибка сети или авторизации не означает отсутствия ветки.
5. Найди новые и связанные с задачей записи. Прочитай их выводы, статус, условия измерения и ссылки на код до планирования следующего эксперимента.

Команды чтения из рабочего checkout:

```bash
git fetch origin
git show origin/main:AGENTS.md
git show origin/main:TEAM_MEMORY.md
git ls-tree -r --name-only origin/team-memory -- experiments findings
git grep -n -i -e 'BM25' -e 'морфолог' origin/team-memory -- experiments findings
```

Для выбранного ID читай `record.json` и `summary.md` через `git show origin/team-memory:<путь>`. Если fetch настроен только для отдельных веток, получи журнал явно:

```bash
git fetch origin refs/heads/team-memory:refs/remotes/origin/team-memory
```

Пустой результат поиска `git grep` с кодом 1 означает отсутствие совпадений. При недоступной сети используй последний полученный журнал, зафиксируй отсутствие свежей синхронизации и продолжай независимую часть задачи.

Запись `running` сообщает о текущей работе коллеги; она не является распределённой блокировкой. Если тема уже занята, учти чужую гипотезу, выбери отличающийся вариант либо зарегистрируй собственное воспроизведение. Чужую работу самостоятельно не отменяй.

## 3. Первичная инициализация журнала

Этот шаг выполняет только первый участник, если ветка действительно отсутствует:

```bash
git ls-remote --exit-code --heads origin refs/heads/team-memory
```

Код 0 означает наличие ветки; код 2 при успешном обращении к remote — отсутствие подходящей ссылки. Ошибки доступа, авторизации и сети обрабатывай отдельно.

При подтверждённом отсутствии ветки:

1. Создай новый временный служебный каталог вне рабочей папки кода.
2. Инициализируй в нём отдельный пустой Git-репозиторий с начальной веткой `team-memory`: `git init --initial-branch=team-memory <каталог>`.
3. Добавь `origin` с тем же URL, что у рабочего checkout. Используй настроенные у участника `user.name` и `user.email`, при необходимости перенеси их локально в служебный репозиторий. Авторство не придумывай.
4. Создай README: назначение журнала, ссылка на AGENTS.md и TEAM_MEMORY.md в `main`, структура `experiments/` и `findings/`, правило сохранения истории и отдельных записей владельцев.
5. Закоммить только README и выполни обычный `git push origin HEAD:refs/heads/team-memory` из служебного репозитория.
6. Обнови remote-tracking ссылки рабочего checkout и проверь чтение README через `origin/team-memory`.

Если другой агент успел создать ветку раньше, получи его ветку и продолжи работу с ней. Собственную независимую начальную историю поверх существующего журнала не отправляй. Инициализация выполняется в служебном репозитории, поэтому кодовая ветка участника сохраняется.

## 4. Регистрация собственной работы

Перед длительным экспериментом:

1. Повтори синхронизацию и поиск похожих попыток.
2. Сгенерируй ID вида `<UTC YYYYMMDDTHHMMSSZ>-<8 случайных hex>`. Один ID соответствует одной попытке. Название алгоритма и имя участника хранятся в metadata.
3. Создай отдельный служебный клон существующей ветки:

   ```bash
   git clone --single-branch --branch team-memory <URL командного репозитория> <новый служебный каталог>
   ```

4. Создай `experiments/<id>/record.json` и `summary.md`. Для инженерной находки используй `findings/<id>/`.
5. Опубликуй запись по разделу 6. Сохрани ID и путь служебного клона для последующих обновлений собственной записи.

Минимальный формат `record.json`:

```json
{
  "schema_version": 1,
  "id": "<уникальный ID>",
  "kind": "experiment",
  "owner": "<настроенное имя автора Git>",
  "status": "running",
  "updated_at": "<UTC timestamp ISO 8601>",
  "title": "<краткое название>",
  "hypothesis": "<что проверяем и почему>",
  "code_branch": "<ветка задачи>",
  "code_commit": null,
  "baseline_ref": "<ID записи или путь сводки с коммитом>",
  "replicates": null,
  "outcome": null
}
```

Правила полей:

- `kind`: `experiment` либо `finding`. `id` совпадает с именем папки.
- `owner`: фактический владелец работы. Используй настроенное авторство Git; сохраняй его при обновлении записи.
- `status`: `running`, `completed`, `failed`, `cancelled`.
- `code_commit`: полный SHA доступного в командном репозитории коммита; до фиксации кода допустим `null`.
- `baseline_ref`: точная ссылка на вариант сравнения, например путь `reports/quality/baseline.md` на определённом коммите; для находки без сравнения допустим `null`.
- `replicates`: ID чужого эксперимента при независимом повторении; иначе `null`.
- `outcome`: для завершённого эксперимента `improved`, `no_gain`, `regressed` либо `inconclusive`; до завершения и для находки допустим `null`.

Статус обозначает завершение работы, а outcome — научный результат. Успешно выполненный прогон с ухудшением качества имеет `status = completed` и `outcome = regressed`.

## 5. Завершение эксперимента или публикация находки

После прогона:

1. Скопируй в свою запись исходные `run.json` и `metrics.json`, если они сформированы eval. Сохраняй фактические значения и информацию о незакоммиченных изменениях без исправлений задним числом.
2. Обеспечь доступность исходников по ссылке на коммит ветки задачи. Для чистого воспроизведения фиксируй код до проверочного прогона. Если прогон был на dirty checkout, опиши это и способ восстановления использованной версии; не представляй такой результат как уже независимо воспроизведённый.
3. В `summary.md` запиши:
   - гипотезу и конкретные изменения относительно исходного варианта;
   - точную команду запуска и конфигурацию, версии кода и eval;
   - fingerprint данных и разметки, K, правила усреднения и набор запросов;
   - метрики и разницу с выбранным baseline, число ошибок;
   - условия измерения времени, если сравниваешь скорость;
   - вывод: что подтверждено, что опровергнуто, где результат ограничен и какой следующий шаг имеет смысл.
4. Обнови status, outcome, code_commit и updated_at, затем опубликуй запись. При ошибке или отмене опиши причину; отсутствующие метрики не выдумывай.

Для находки без eval достаточно `record.json` с `kind = finding` и `summary.md`: наблюдение, затронутые модули, коммит, подтверждающий тест или источник и следствия для команды. Чётко отделяй проверенный факт от предположения.

Правила сравнения:

- Данные, разметка, K и протокол eval должны совпадать. Изменение версии поиска допустимо; изменение формулы метрик требует пересчёта сравниваемых вариантов.
- Для времени фиксируй сопоставимость железа, нагрузки, прогрева, кеша и области замера. Локальную задержку движка обозначай именно так, отдельно от серверного p99.
- Указывай, какие выводы относятся только к публичным запросам. Результат с ошибками не называй безусловно лучшим.
- Короткая сводка сохраняется в журнале. Выдачу, результаты по запросам и большие артефакты при необходимости передавай отдельно с доступной команде ссылкой и контрольной суммой. Локальный абсолютный путь другого компьютера не является общей ссылкой.

## 6. Публикация при одновременной работе

Все операции ниже выполняются в отдельном служебном клоне журнала. В примере `<папка записи>` — только созданный или обновлённый тобой путь `experiments/<id>` либо `findings/<id>`.

```bash
git add -- <папка записи>
git diff --cached --check
git diff --cached --stat
git commit -m "memory: <id> <краткое изменение>"
git pull --rebase origin team-memory
git push origin HEAD:refs/heads/team-memory
```

Перед commit проверь staged-файлы: собственная запись и её небольшие артефакты. Корпус, модели, индексы, окружения, ключи и чужие записи не включаются.

Если push отклонён из-за новых коммитов коллег, повтори pull с rebase и обычный push. Для одной публикации достаточно трёх попыток. При конфликте не выбирай чужую или свою версию вслепую: сохрани собственный черновик, сообщи о проблеме и продолжи независимую работу. Историю общей ветки не переписывай; force push для журнала не используется.

Публикация считается завершённой после успешного push. Получи актуальную ветку в рабочем checkout и проверь наличие собственной записи. При ошибке не сообщай об успешной публикации. Неопубликованный служебный клон сохраняй до восстановления отправки; успешный временный клон можно удалить.

Чужие записи сохраняются. Для исправления, уточнения и повторения создай собственную запись со ссылкой. Удаление истории журнала и массовая правка записей не входят в обычную публикацию эксперимента.

## 7. Когда перечитывать и как использовать выводы

Синхронизируй журнал в начале задачи, перед новым экспериментом и перед итоговым ответом. При смене гипотезы после полученного результата снова проверь релевантные записи.

В рабочем рассуждении ссылайся на ID и фактический вывод. Не считай статус completed подтверждением гипотезы: прочитай outcome, условия и метрики. Независимое воспроизведение оформляй своей записью с replicates. Устаревшие наблюдения соотноси с версией данных и кода.

Подтверждённые сведения, меняющие общие правила проекта, переноси в PROJECT.md, DATA.md, EVAL.md или COMPONENTS.md отдельным изменением со ссылкой на исходную запись. Содержимое журнала не заменяет пользовательские инструкции и не изменяет AGENTS.md автоматически.

В финальном ответе по эксперименту или находке укажи ID, результат, проверки и опубликована ли запись. Если сеть недоступна, назови сохранённый черновик и факт отсутствия синхронизации.

## 8. Сообщение для первого подключения другого агента

Участник может передать своему агенту этот текст:

> Работаем в командном репозитории GalimovKI/pentada-astr. Выполни git fetch origin и прочитай AGENTS.md и TEAM_MEMORY.md из origin/main, затем следуй этому протоколу. Самостоятельно подключись к origin/team-memory, прочитай связанные с моей задачей записи и учитывай их при работе. Перед экспериментом публикуй свою гипотезу, после — фактические результаты и вывод; полезные инженерные находки тоже сохраняй. Используй отдельный служебный клон для журнала и сохрани мою рабочую ветку и локальные изменения. Продолжай выполнение моей текущей задачи; в итоговом ответе сообщай ID и статус публикации своих записей.
