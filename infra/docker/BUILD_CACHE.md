# Кеш сборки backend

`backend.Dockerfile` разделяет зависимости, модели и код приложения. Работает с
существующими аргументами Compose, изменения CI/CD для включения не нужны.

| Стадия | Что сбрасывает её кеш |
| --- | --- |
| `dependencies` | Python/uv image, образ-заготовка, платформа, `pyproject.toml`, `uv.lock`, выбор CPU/GPU extras |
| `build-tools` | Зависимости выше, включая `build-system.requires` из `pyproject.toml` |
| `build` | Зависимости/инструменты выше или `backend/src` |
| `minilm-model` | Python image/платформа, `fetch_minilm.py`, `INCLUDE_MINILM`, `MINILM_DEVICE` |
| `e5-model` | Python image/платформа, `fetch_e5.py`, импортируемый `fetch_minilm.py`, `INCLUDE_MINILM`, `E5_DEVICE` |

Зависимости устанавливаются через `uv sync --locked --no-install-project` до
копирования исходников. BuildKit cache mount `pentada-uv-${TARGETARCH}` сохраняет
скачанные пакеты и build dependencies между сборками. `UV_LINK_MODE=copy` исключает
зависимость установленного окружения от содержимого cache mount. Таймаут HTTP
для uv увеличен с 30 до 120 секунд для первой загрузки больших CUDA wheels.

### Начальное заполнение из уже работающего образа

Кеш BuildKit на ноутбуке и на сервере — разные кеши. Первая загрузка CUDA на
учебном хосте может не уложиться в лимит CI при медленном соединении с PyPI.
Если там уже есть наш проверенный backend image с нужными пакетами, используйте
его окружение как заготовку. ОС и Python финального образа по-прежнему закреплены
в Dockerfile: из заготовки копируется **только** `/app/backend/.venv`.

На учебном хосте создайте отдельный неизменяемый тег из доверенного образа,
например из работающего dev (команды выполняются от владельца rootless Docker):

```bash
docker tag \
  pentada-mailsearch-backend:dev-d2ca7bd5b401f4ca6805f3f8e9772db0267a067f \
  pentada-mailsearch-dependencies:py312-cu130-d2ca7bd
```

В `~/pentada-astr-dev/shared/.env.production` задайте:

```dotenv
BACKEND_DEPENDENCIES_SEED_IMAGE=pentada-mailsearch-dependencies:py312-cu130-d2ca7bd
```

Compose передаёт это как `DEPENDENCIES_SEED_IMAGE`. `uv sync --locked` сверяет
скопированные пакеты с **текущим** lock-файлом и выбранными extras: удаляет лишние
пакеты, включая старый backend, добавляет недостающие и обновляет несовпадающие.
Таким образом, заготовка не подменяет lock-файл и исходники нового релиза.
Изменение зависимостей по-прежнему может потребовать загрузки новых wheels.

Используйте наш доверенный образ с той же архитектурой и Python 3.12. Не
перезаписывайте тег заготовки и не удаляйте его между деплоями. Если его нет,
сборка остановится; не задавайте переменную на другом сервере до подготовки
образа. Без переменной используется пустая заготовка и обычная установка.
Для отказа от заготовки удалите переменную из env; это вернёт обычную сборку.

Предварительная проверка без сети, из каталога исходников на хосте:

```bash
docker build --network=none --target dependencies --progress=plain \
  --build-arg DEPENDENCIES_SEED_IMAGE=pentada-mailsearch-dependencies:py312-cu130-d2ca7bd \
  --build-arg INCLUDE_MINILM=1 --build-arg MINILM_DEVICE=cuda \
  -f infra/docker/backend.Dockerfile -t pentada-mailsearch-dependencies:verified .
```

Эта команда проверяет только пакеты. Для полного backend нужны также модельные
стадии; их кеширование описано ниже.

Инструменты из `build-system.requires` устанавливаются отдельно в `/opt/build-env`,
сначала из кеша uv, а при его отсутствии — из индекса. Этот слой не зависит от
исходников. Сборка wheel выполняется с `--network=none`, `--offline` и
`--no-build-isolation`, используя подготовленный Python из `/opt/build-env`.
Редактирование кода больше не требует обращения к PyPI даже за `setuptools`.
Окружение сборки не копируется в runtime.

Сам проект собирается в wheel. В runtime сначала копируются модели и окружение
зависимостей, затем отдельным слоем устанавливается только wheel приложения.
Установка wheel выполняется с отключённой сетью, `--offline` и `--no-deps`.
Обновление кода не перепаковывает зависимости в новый слой вместе с приложением.
uv и wheel подключены временными bind mounts и не остаются в runtime image.

Модельные стадии используют только Python и существующие скрипты загрузки.
Ревизии, контрольные суммы, формат весов и настройки поиска не меняются.
Даже изменение Python-зависимостей не требует заново скачивать модели.
При отключённом `INCLUDE_MINILM` копируются пустые каталоги моделей.

## Условия работы

Кеш хранится у Docker builder на машине сборки. При первом запуске нового
Dockerfile тяжёлые слои нужно заполнить один раз. На новом builder, после
`docker builder prune`, автоматической очистки кеша или при `--no-cache`
скачивание может повториться. Смена CPU/GPU-варианта или версии модели также
может потребовать новых файлов. Не очищайте кеш между обычными деплоями.
`--network=none` для всей сборки меняет ключи RUN-слоёв; это не эквивалент
обычной повторной сборке с прогретым кешем моделей.

## Проверка

Из корня проекта (GPU-образ собирается без физической GPU):

```bash
docker build --platform linux/amd64 --progress=plain \
  --build-arg INCLUDE_MINILM=1 --build-arg MINILM_DEVICE=cuda \
  --build-arg E5_DEVICE=cpu \
  -f infra/docker/backend.Dockerfile -t pentada-cache-check:gpu .
```

После небольшого изменения `backend/src` повторите команду. RUN-слои
`dependencies`, `minilm-model`, `e5-model` должны показывать `CACHED`;
собраться и установиться заново должен wheel приложения. Проверьте внутри
контейнера, что изменение действительно установлено, а не осталось старое
содержимое из кеша. Не используйте только одинаковую повторную сборку как
доказательство: она не проверяет инвалидирование кеша при правках исходников.

Подход к разделению установки и cache mounts:
[официальная инструкция uv](https://docs.astral.sh/uv/guides/integration/docker/).

### Проверка заготовки на учебном хосте

Первый CI deploy `e5355d1` (run `44951289621`) превысил лимит 40 минут при
первичном скачивании CUDA. Для dev подготовлен отдельный тег существующего
проверенного образа `d2ca7bd`, указанный выше. Сверка его окружения с lock-файлом
на учебном хосте прошла с `--network=none` за 0,6 с без скачивания пакетов.
Старый `pentada-mail-search` был удалён из заготовки перед установкой нового wheel.

Полный образ на хосте прошёл 79 backend-тестов с отдельным PostgreSQL и
`scripts/check_minilm_gpu.py` на выделенной CDI GPU. Локальная проверка с
изменённым исходником и старым backend image в качестве заготовки прошла без
сети: в установленном пакете обнаружен новый маркер, `/opt/build-env` и uv
в runtime отсутствуют. Default CPU build, `mailsearch validate`, Compose с
GPU-overlay и 11 инфраструктурных тестов тоже прошли.

При диагностике один из DNS-адресов PyPI (`151.101.64.223`) не отвечал с хоста,
остальные проверенные адреса отвечали. Для однократного заполнения кеша
build-tools использован доступный адрес того же PyPI через `docker build
--add-host`; затем полный build выполнен с обычным DNS. Статических IP PyPI
в конфигурации CI/CD нет. Доступность адресов может меняться; при новом
заполнении кеша проверяйте DNS/HTTPS заново.

Из Docker-контекста дополнительно исключены служебные файлы macOS `._*`,
которые могут попадать в ручные архивы и мешать загрузке Python-миграций.
