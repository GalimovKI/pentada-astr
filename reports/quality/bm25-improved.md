## Где публичный набор оставляет пробелы

- Все 99 запросов содержат дату получения и указывают на предыдущий календарный день. После удаления распознанной фразы о дате, начального «найди/покажи» и нормализации пробелов и пунктуации остаётся **12 разных текстов запросов**. Два самых частых шаблона дают 48 из 99 запросов.
- У **5 из 12 ящиков** нет публичных запросов. В них **6 427 писем (39,25% корпуса)**, включая 91 письмо с неизвестной датой получения.
- Для отдельной диагностики использованы **42 запроса с одним размеченным целевым письмом**. У каждого убрана распознанная фраза о дате получения, сохранены ящик, `query_date` и целевой `doc_id`. Изменённые запросы могут стать неоднозначными. Метрики ниже показывают позицию исходного целевого письма. Для оценки общей релевантности нужен отдельный набор с независимой разметкой.

| Вариант | Цель в top-10 без даты | MRR@10 без даты | MRR@10 с исходной датой |
| --- | ---: | ---: | ---: |
| BM25 со Snowball | 16/42 | 0,138 | 0,976 |
| Улучшенный BM25 | 19/42 | 0,170 | 0,988 |

Воспроизведение диагностики. Из `load_dataset` оставить только `Query` с одним положительным `qrel`. Для копии каждого запроса заменить `query` вторым элементом `receipt_day(query, query_date)`, убрать `" ,."` с краёв. Выполнить `run_engine` на обеих копиях набора с K = 10 и посчитать метрики через общий `evaluate` с исходным целевым письмом.

## Как расширить проверку

Сначала собрать отдельный набор из 40–60 новых запросов к письмам выданного корпуса. Начать с пяти ящиков без публичных запросов. Включить перефразировки без даты, точные номера, даты событий и интервалы. Для предметных запросов проверить объединённый top-20 BM25 и E5 и добавить известные цели вручную. Это снижает риск принять ещё одно подходящее письмо за ошибку. Сценарии без результата оценивать отдельно по доле лишних выдач. Разделять наборы для настройки и финальной проверки по ящикам или темам. Держать исходный публичный прогон с прежним корпусом для сопоставимости.

Внешние данные лучше использовать в отдельном эксперименте. Даже письма из дополнительных ящиков изменят статистику всего корпуса в новом BM25.

- Для независимой проверки поиска по почте доступны темы и оценки известного письма и обсуждений в англоязычном корпусе W3C. [NIST TREC Enterprise](https://trec.nist.gov/data/t14_enterprise.html)
- Для проверки поиска по русскоязычным перефразировкам можно использовать отдельный retrieval-бенчмарк на Википедии. Он проверяет другой тип текстов и не измеряет работу с ящиком или датами. [MIRACL, русский раздел](https://github.com/project-miracl/miracl#topics-and-relevance-judgments)
- Для отдельной нагрузки, объёма индекса и устойчивости обработки почтового текста подходит Enron. Публикуемый архив содержит около полумиллиона сообщений, а эксперименты по качеству требуют запросов с разметкой. [Архив Enron, Carnegie Mellon](https://www.cs.cmu.edu/~enron/)
