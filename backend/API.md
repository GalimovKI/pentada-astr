# HTTP API v1

Реализация: FastAPI/Pydantic/Uvicorn. Все маршруты данных используют контекст
демонстрационного ящика, который **не является авторизацией**. Поле `doc` — исходный
текст, включая возможную HTML-разметку; клиент должен отображать его как текст.
Полей темы, отправителя или вложений нет. `doc_dt: null` сохраняется.

## Контракт

Даты сценария обязательны, только календарный `YYYY-MM-DD`, включая синтетические
будущие годы. Известные письма после `query_date` исключаются. Неизвестный ящик —
404; отсутствующее, чужое и будущее письмо имеют одинаковый 404.
Список ящиков упорядочен по ID. Письма: дата по убыванию, затем ID по возрастанию;
NULL-даты последними. Поиск сохраняет порядок движка.

| Метод и путь | Параметры | Ответ 200 |
| --- | --- | --- |
| `GET /api/v1/mailboxes` | — | `{"items":["a","b"]}` |
| `GET /api/v1/mailboxes/{synthetic_user}/messages` | `query_date`, `limit` (1–500, по умолчанию 50), `cursor` (до 4096 символов) | `{"items":[{"doc_id":"d1","synthetic_user":"a","doc_dt":null,"snippet":"Текст"}],"next_cursor":null}` |
| `GET /api/v1/mailboxes/{synthetic_user}/messages/{doc_id}` | `query_date` | `{"item":{"doc_id":"d1","synthetic_user":"a","doc_dt":null,"doc":"Полный исходный текст"}}` |
| `POST /api/v1/mailboxes/{synthetic_user}/search` | JSON ниже | `{"items":[{"doc_id":"d1","synthetic_user":"a","doc_dt":null,"snippet":"Текст","score":1.25}]}` |
| `POST /api/v1/spelling` | JSON `query`, необязательные `cursor` и `expand_word_forms` | `changes` и `completions` |
| `GET /health/live` | — | `{"status":"live"}` |
| `GET /health/ready` | — | `{"status":"ready"}` |

Тело поиска: `{"query":"Найди письмо о переносе встречи","query_date":"2028-09-11","limit":10}`.
`query` — непустая строка до 4000 символов, пробельный запрос отклоняется.
`limit` поиска — целое 1–100, по умолчанию 10, без boolean, строк и дробей.
Лишние поля тела запрещены. Фрагменты — первые 200 символов, извлекаемые в SQL;
полный текст возвращается только при открытии письма. `total` отсутствует.
Пустой результат — `{"items":[]}` с 200. Разметка и qrels в ответах отсутствуют.

Поиск принимает флаги `correct_typos` и `expand_word_forms` в теле запроса. Оба по умолчанию выключены. При включённом `correct_typos` сервер проверяет слова по отдельности. При включённом `expand_word_forms` сервер разбирает русские слова в каждой фразе через `pymorphy3`. Например, «новые посылочки приехали» даёт поисковые термы «новый посылка приехать». Для уменьшительных форм локальная модель учит суффиксные преобразования на 2 206 парах из Викисловаря и сверяет предполагаемую основу с морфологическим словарём. Так «штрафиками» даёт «штраф», хотя в обучающих примерах этого корня нет. Для слов с несколькими разборами учитываются соседние слова, а при недостатке контекста используются вероятности разборов морфологической модели. Исходная фраза остаётся запасным вариантом поиска. Артикулы и адреса сохраняются целиком.

Если основной запрос вернул меньше `limit` писем, поиск дополняет выдачу по исправленной формулировке и связанным формам. Все варианты используют тот же ящик и фильтр даты получения, повторяющиеся письма пропускаются. Параметр URL `explain=true` добавляет `receipt_date` и найденный фрагмент `passage`. Смещения подсветки в `passage` измеряются в единицах UTF-16.

В `/spelling` поле `cursor` и диапазоны `start`, `end` в предложениях измеряются в кодовых точках Unicode. Сервер предлагает изменения текста, выбор применяет клиент.

Все ошибки имеют `{"error":{"code":"..."}}`, без входных значений и traceback:

| HTTP | Коды |
| --- | --- |
| 404 | `mailbox_not_found`, `message_not_found` |
| 422 | `validation_error`, `invalid_cursor` |
| 503 | `service_unavailable`, `engine_unavailable`, `engine_metadata_missing`, `database_unavailable`, `import_metadata_missing`, `dataset_mismatch` |
| 500 | `engine_failure`, `engine_contract_violation`, `internal_error` |

Прочие HTTP-ошибки используют `http_error` и исходный статус, например 405.
Готовность проверяет доступность схемы БД и fingerprint успешного импорта.
При ошибке загрузки сервер остаётся живым для диагностики, readiness и маршруты
данных возвращают 503; автоматического fallback или пустой выдачи нет.
После временной ошибки БД готовность восстанавливается при успешной проверке.
После ошибки загрузки/конфигурации движка требуется исправление и перезапуск.

Курсор: URL-safe base64 JSON с полями `v:1`, `synthetic_user`, `query_date`,
`doc_dt` (дата или null), `doc_id`. Контекст и версия проверяются. Повреждение,
несовпадение контекста или недопустимая дата дают 422. Это позиция стабильной
keyset-пагинации, не средство авторизации и не подписанный токен.

OpenAPI: `/openapi.json`, интерактивная документация: `/docs`.

## Жизненный цикл и конкурентное исполнение

На процесс создаются один SQLAlchemy engine/пул и один поисковый движок.
Загрузка, все вызовы `SearchEngine.search`, материализация результата и `close`
исполняются последовательно в одном выделенном потоке. Это поддерживает движки
с привязкой к потоку и не предполагает потокобезопасности. SQL и маршруты данных
выполняются в worker threads FastAPI; event loop не выполняет поиск и SQL.
См. [модель исполнения FastAPI](https://fastapi.tiangolo.com/async/).
При остановке ожидаются принятые задачи, вызывается `LoadedEngine.close`,
завершается executor, закрывается пул, в том числе при ошибке инициализации.
Загрузчик отвечает за очистку частично созданных ресурсов, если сам выбрасывает
исключение до возврата `LoadedEngine`.

Первый запуск: `--workers 1`, без reload. Несколько процессов означают отдельные
копии модели и индекса. Параллельные поиски ожидают единственный поток движка;
очередь и worker pool не обеспечивают ограниченную задержку при перегрузке.
Гарантированный timeout вычисления и полный нагрузочный стенд не реализованы.

`Server-Timing: search;dur=...` возвращает миллисекунды от входа HTTP-запроса в
middleware до подготовленного ответа, включая чтение тела, валидацию, ожидание
worker pool и потока движка, SQL, сериализацию и ошибки обработанных запросов.
Сеть до приложения и отправка тела клиенту не входят. Тот же замер с HTTP-статусом
доступен через INFO logger `mail_search.api` (уровень настраивается оператором).
Тексты запросов, писем, SQL, секреты и пути в прикладные логи не записываются.
Это точки для будущего нагрузочного теста, не заявление о серверном p99.
Встроенный access log Uvicorn в инструкции выключен: URL открытия письма содержит ID.
CORS не включён; локальный frontend использует Vite proxy `/api`, поэтому
разрешения CORS не требуются. При отдельном origin без proxy потребуется явный
список разрешённых origins.

## Настройки и подключение движка команды

Только серверные переменные, HTTP-клиент не задаёт пути или Python-модули:

- `DATABASE_URL` — PostgreSQL URL, включая параметры TLS; обязательна для сервера.
- `SEARCH_ENGINE_FACTORY` — `module:callable`, по умолчанию
  `mail_search.core.engine:load_event_aware`.
- `SEARCH_CONFIG` — JSON объекта конфигурации, по умолчанию
  `configs/search/bm25-event-aware.json` от корня checkout. При передаче
  только `SEARCH_CONFIG` сохраняется поддержка старых конфигураций BM25.
  Для явного конфига нового движка задайте обе переменные.
- `SEARCH_DATASET` — проверенный архив/каталог или путь к артефактам будущего
  загрузчика; по умолчанию `data/raw/mipt_mail_search_participants.zip` от checkout.

Явные относительные пути считаются от каталога запуска. Настройки Pydantic
проверяют форму module path; PostgreSQL loader проверяет URL; конкретный загрузчик
проверяет файлы, параметры и совместимость своих артефактов. Секрет URL скрыт
в представлении настроек. `.env` загружает `uv --env-file`, само приложение не
читает его автоматически. При ошибке старта лог содержит только категорию ошибки.

Новый серверный загрузчик принимает `Settings`, возвращает `LoadedEngine`:

```python
from mail_search.core.engine import LoadedEngine
from mail_search.domain.models import SearchRequest, SearchHit


def load_engine(settings):
    # Проверить settings.search_config и settings.search_dataset, загрузить
    # готовую модель, индекс и manifest. При ошибке освободить свои ресурсы.
    engine = ...
    fingerprint = ...  # manifest набора, из которого построен индекс
    return LoadedEngine(engine=engine, fingerprint=fingerprint, close=engine.close)

# engine.search(request: SearchRequest, k: int) -> Sequence[SearchHit]
# SearchRequest: query, synthetic_user, query_date
# SearchHit: doc_id, score (конечное число)
```

Фабрику устанавливают в том же Python-окружении, указывают её доверенный путь в
`SEARCH_ENGINE_FACTORY`; конфигурацию кладут в `configs/search/`, большие индексы
и модели — в `artifacts/` вне Git. Никаких изменений маршрутов, схем или storage.
Загрузчик отвечает за модель и индексы, их версии, проверку конфигурации и cleanup.
Движок отвечает за фильтрацию ящика и известных будущих писем, относительные даты
от `query_date` и окончательный порядок. Нельзя использовать qrels в ранжировании.

API независимо проверяет уникальность ID, размер выдачи, тип hit и конечность score,
затем одним пакетным запросом previews проверяет доступность каждого результата.
Нарушение — 500, без скрытого исправления порядка, пропуска или добора документов.
Неизвестный, чужой и будущий ID не раскрываются. Загрузчик и движок должны завершать
свои синхронные операции; API не прерывает зависший Python-вызов.

`load_event_aware` читает набор через `load_dataset`, строит индексы для
`search.event_aware:create_engine(documents, config)` и возвращает fingerprint.
`load_bm25` доступен для прежних конфигураций.
Загрузчик видит валидированный набор, но в фабрику ранжирования передаются только
документы и конфигурация. Offline eval API не импортирует и работает без БД.

Fingerprint сохраняет исходную семантику `ingestion/dataset.py`: SHA-256 от JSON
со словарём хешей README, documents.jsonl, queries_dev.jsonl и qrels_dev.jsonl,
с `sort_keys=True`. Это не только хеш документов и не хеш ZIP. Команда индексов
должна сохранить этот fingerprint в manifest при подготовке. API сравнивает его
с `corpus_import.fingerprint` версии формата 1 на старте и перед чтениями.
Отсутствующие метаданные и несовпадение дают 503. Импорт должен оставаться
неизменяемым; произвольные ручные изменения SQL после импорта не обнаруживаются
одним fingerprint и не поддерживаются.

Миграции, импорт, обучение и запись индексов автоматически не выполняются.

## Проверка настоящего сервера

После запуска Uvicorn команда (из корня checkout):

```bash
uv run --project backend --locked --env-file .env python scripts/check_http_api.py
# Для другого порта: ... scripts/check_http_api.py --url http://127.0.0.1:8017
```

Это read-only регрессия на предоставленном официальном корпусе: все 99 запросов
сравниваются с прямым вызовом текущего BM25 со стеммингом, проверяются previews,
открытие первого результата, 12 ящиков и полная пагинация одного ящика с NULL.
Для проверки другого алгоритма используйте общий eval и отдельные тесты: этот
скрипт намеренно проверяет именно исходную интеграцию BM25, не качество моделей.
