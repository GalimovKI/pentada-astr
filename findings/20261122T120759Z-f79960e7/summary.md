# Что видит пользователь публичного поиска SmartMail

При открытии страницы видны логотип, строка и кнопка «Найти». Приложение получает список доступных ящиков для выбора контекста. Письма загружаются после запроса. Пользователь может открыть найденное письмо, вернуться к результатам и очистить поиск. На телефоне открытое письмо занимает область результатов. Код проверенной сборки зафиксирован в [PR № 20](https://github.com/GalimovKI/pentada-astr/pull/20), [коммит 6ff09ba](https://github.com/GalimovKI/pentada-astr/commit/6ff09bae6b42edd4e33302202f0045c46db2b163).

Во время ввода строка предлагает принять исправление опечатки или продолжение слова. При отправке поле сохраняет введённый текст, а сервер исправляет опечатку и ищет сначала по основной форме. Например, `штрфаик` → `штрафик` → `штраф`. Для правильно написанного `оштрафовали` сервер сразу выбирает `штраф`. Если основной запрос вернул меньше запрошенного количества результатов, поиск может добавить письма по остальным вариантам. Запросы используют один ящик и дату, повторные письма исключаются. Список словообразовательных семейств в этой версии задан явно. [Обработка запроса](https://github.com/GalimovKI/pentada-astr/blob/6ff09bae6b42edd4e33302202f0045c46db2b163/backend/src/mail_search/api/app.py), [семейства слов](https://github.com/GalimovKI/pentada-astr/blob/6ff09bae6b42edd4e33302202f0045c46db2b163/backend/src/mail_search/application/word_forms.py).

## Локальные проверки

- Chromium на десктопном и мобильном экранах прошёл 32 сценария с подменой ответов API. Ещё два прогона с реальными FastAPI, PostgreSQL и корпусом проверили порядок результатов на экране относительно ответа API, текст открытого письма, возврат и очистку. Для проверки из `frontend` используются `npm run test:browser` и `npm run test:real` с запущенным сайтом, адресом в `PLAYWRIGHT_BASE_URL` и импортированным корпусом. [Браузерный тест на реальных данных](https://github.com/GalimovKI/pentada-astr/blob/6ff09bae6b42edd4e33302202f0045c46db2b163/frontend/tests/real/real.spec.ts).
- На контрольном ящике `box-12259a301ee2` с датой `2030-01-01` запросы `штрфа`, `штрфаик`, `штрафик` и `оштрафовали` дали основной вариант `штраф` и по 10 результатов при лимите 10. Это проверка порядка обработки. У этих диагностических вариантов нет отдельной разметки релевантности. [Тест исправления опечатки](https://github.com/GalimovKI/pentada-astr/blob/6ff09bae6b42edd4e33302202f0045c46db2b163/backend/tests/unit/test_spelling.py).
- Для 99 исходных размеченных запросов одного корпуса Mail Public прогнали `correct_query` → `search_queries` → `MailService.search` с BM25 с учётом событий и общим `evaluate`. Движок получил до 100 результатов на запрос, метрики усреднены по запросам при K=10. Контрольный прямой вызов BM25 и серверная логика с исправлением показали одинаковые значения: Recall@10 **0,937564**, nDCG@10 **0,997610**, MRR@10 **1,000000**. Fingerprint корпуса `0daa664136d798c1ed2fe50802a7d236f93b4891d56f2353bc5b807b56601665`. В этой проверке хранилище читало те же документы из памяти. Вывод ограничен исходными публичными запросами и одним корпусом. Для оценки качества на опечатках нужна отдельная размеченная выборка.
