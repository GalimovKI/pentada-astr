# Умный поиск в Почте

Описание проекта команды для кейса VK Tech на хакатоне МФТИ. Документ фиксирует известные требования и условия оценки, проектные решения команды и вопросы, которые ещё предстоит уточнить.

Устройство продукта и порядок разработки: [COMPONENTS.md](COMPONENTS.md). Форматы и результаты проверки предоставленного корпуса: [DATA.md](DATA.md).

Текущий этап — локальный eval и исходный BM25-бейзлайн: [запуск и правила оценки](EVAL.md), [первый результат](reports/quality/baseline.md).

2. Презентация «Умный поиск в Почте»: страницы 34–44 общего файла «Презентации_хакатона_единый_файл.pdf», слайды 01–11 кейса VK Tech.
3. Архив участников `mipt_mail_search_participants.zip`: README организаторов, manifest и публичные данные. Состав, контрольные суммы и подтверждённые свойства описаны в [DATA.md](DATA.md).

Требования организаторов приведены в разделах 3–6. Решения команды приведены отдельно в разделе 7. Неопределённые условия перечислены в разделе 8 и не считаются установленными правилами хакатона. Числа и примеры со слайдов не задают отсутствующие пороги качества, значения K или формулу итогового балла.

## 2. Цель продукта и пользовательский сценарий

Пользователь помнит содержание письма, но не помнит его точную тему, отправителя или формулировки. Продукт должен помогать находить письмо по описанию своими словами, в том числе когда слова запроса и письма отличаются.

Основной сценарий:

1. Пользователь открывает веб-прототип почты и просматривает доступные письма.
2. Описывает нужное письмо естественным языком.
3. Получает ранжированные результаты поиска.
4. Открывает найденное письмо и читает его содержимое.

Пример из презентации: запрос о том, что самолёт улетит позже, должен помогать находить письмо об изменении времени вылета. Примеры иллюстрируют назначение продукта и не являются известным полным набором проверочных запросов.

## 4. Данные и оценка качества

Предоставленный архив содержит **16 376 псевдонимизированных писем в 12 синтетических ящиках**, **99 публичных запросов** и **565 связей релевантности**. Количество строк и контрольные суммы SHA-256 совпали с manifest. В README архива тексты и даты описаны как синтетические.

Данные представлены в UTF-8 JSONL: письма в `documents.jsonl`, запросы в `queries_dev.jsonl`, разметка в `qrels_dev.jsonl`. Текст письма хранится единым полем `doc`; отдельных полей темы, отправителя, HTML и вложений в схеме нет. Подробные поля и статистика приведены в [DATA.md](DATA.md).

Предусмотрены два бенчмарка:

- **Публичный:** 99 запросов для разработки, экспериментов и самостоятельной проверки.
- **Приватный:** итоговая оценка качества и скорости организаторами; приватные тесты участникам не раскрываются, решения запускают организаторы.

### R09. Контекст ящика и даты

README предоставленного архива уточняет правила выполнения каждого запроса:

- Поиск выполняется в ящике, указанном в `synthetic_user` запроса.
- `query_date` задаёт дату запроса и точку отсчёта для относительных периодов, включая «вчера».
- Письмо с известной датой получения `doc_dt > query_date` ещё недоступно и не должно попадать в выдачу.
- Даты имеют формат `YYYY-MM-DD`; `doc_dt = null` означает неизвестную дату получения.

Для бенчмарка используется дата из записи запроса, а не текущая дата сервера. Правило обработки неизвестной даты при явно заданном периоде в README полностью не определено; рабочее решение команды выделено в разделе 7.

### R06. Метрики качества

В презентации указаны Recall@K, nDCG@K и MRR@K (PDF, стр. 38 и 40):

| Метрика | Что характеризует |
| --- | --- |
| Recall@K | Долю релевантных писем, попавших в первые K результатов. |
| nDCG@K | Качество порядка выдачи с учётом релевантности и позиции писем. |
| MRR@K | Позицию первого релевантного письма в первых K результатах. |

Публичная разметка бинарная: все 565 записей имеют `relevance = 1`. Согласно README архива документы без строки релевантности для данного запроса получают нулевую оценку при расчёте метрик. У каждого из 99 запросов есть хотя бы один релевантный документ.

README предлагает локально считать Recall@K и nDCG@K по публичной таблице, а MRR@K для поиска конкретного письма — по запросам с одним релевантным документом. В текущем наборе таких запросов **42**. Это рекомендация локальной проверки, а не установленная формула итогового балла.

Значения K, окончательные правила усреднения и веса метрик в итоговом балле неизвестны. Примеры с K = 5 на слайде не устанавливают K для официальной проверки. Отдельный обязательный численный порог качества в предоставленных материалах не указан.

## 5. Скорость, модели и свобода реализации

### R07. Скорость поиска

Требование: **99-й перцентиль времени выполнения поисковых запросов должен быть строго меньше 1 секунды (`p99 < 1 с`)**.

- Начало измерения — получение запроса сервером.
- Конец измерения — готовая поисковая выдача.
- В измерение входят обработка запроса, поиск и ранжирование.
- Сеть между браузером и сервером и отрисовка интерфейса не входят в измерение.
- Нарушение приводит к штрафу в итоговой оценке, а не к дисквалификации.

Размер штрафа, нагрузка, набор запросов, правила прогрева и кеширования будут определены отдельно. Источники: скриншот; PDF, стр. 41.

### R08. Использование моделей

Внутри поискового движка, на этапах отбора кандидатов (**retrieval**) и повторного ранжирования (**reranking**), использование API-моделей или моделей **больше 3 млрд параметров** приводит к снижению оценки. Это не является автоматической дисквалификацией.

За использование API и больших моделей вне поискового движка штрафа нет. Размер модельного штрафа будет определён отдельно. Приоритет кейса — быстрый поиск и самостоятельная проработка поисковых алгоритмов. Источники: скриншот; PDF, стр. 41.

### Свобода реализации

- Команда самостоятельно выбирает алгоритмы, индексы, архитектуру и пользовательские сценарии.
- Показанный в презентации конвейер является примером; reranking необязателен.
- Вычислительные ресурсы не ограничены согласно одностраничному заданию.
- Качественный и быстрый поиск — основная задача кейса; конкретный стек не задан.

Свобода по ресурсам и архитектуре не отменяет требования к p99 и условий штрафа за модели.

## 7. Проектные решения команды

Следующие положения определяют текущий план продукта, а не дополнительные требования организаторов:

| ID | Решение |
| --- | --- |
| P01 | Первый вариант работает со статическим предоставленным корпусом; подготовка данных и построение индексов выполняются до пользовательского поиска. |
| P02 | Пользователь выбирает ящик. Просмотр и поиск ограничиваются выбранным ящиком. Адаптер публичного бенчмарка передаёт в движок `synthetic_user` и `query_date` из записи запроса. |
| P03 | Веб-приложение, eval качества и проверка скорости используют одну реализацию поискового движка и явно заданные конфигурации. |
| P04 | Эксперименты сохраняют выдачу, метрики, версию корпуса и индексов, конфигурацию и версию кода для воспроизведения и сравнения. |
| P05 | Сначала создаются минимальный поиск и eval, затем поиск улучшается по измерениям; далее собирается веб-демонстрация. |
| P06 | Компоненты описываются как логические модули приложения и инструменты для офлайн-запусков. Локальные eval и поиск работают на Python 3.11+. Для BM25 доступны исходный вариант и конфигурация со Snowball и распознаванием даты получения. |
| P07 | Для хранения писем, ящиков и метаданных используется PostgreSQL. Способ хранения поисковых индексов и векторов выбирается отдельно; это решение само по себе не предусматривает использование pgvector. |
| P08 | Неизвестная дата `doc_dt = null` сохраняется. Такой документ не исключается как заведомо будущий, но неизвестная дата не считается подтверждением попадания в явно заданный период. Политику для таких периодов требуется уточнить. |
| P09 | Веб-демо позволяет задать дату поискового сценария и передаёт её явно. Синтетические даты корпуса и бенчмарка, в том числе даты после текущего дня, не подменяются системным временем. |

В основной объём входят подготовка корпуса, хранение и просмотр писем, индексация, поиск, eval, проверка скорости, API, интерфейс и воспроизводимый запуск. Подключение реальных почтовых аккаунтов, отправка писем и синхронизация в основной объём не входят. Бонусные функции рассматриваются после выполнения основной задачи.

Проектные критерии готовности компонент, проверки и связь с требованиями описаны в [COMPONENTS.md](COMPONENTS.md).

## 8. Открытые вопросы

| Тема | Что требуется узнать |
| --- | --- |
| Неизвестные даты | Как учитывать `doc_dt = null` при запросе за конкретный день или период; допустимо ли восстанавливать дату из текста и как это оценивается. |
| Приватный бенчмарк | Совпадают ли его формат, схема разметки и правила временного контекста с публичными; возможны ли запросы без релевантных документов. |
| Метрики | Значения K, правила усреднения и обработки запросов без релевантных документов, официальное использование MRR на всех запросах или на подмножестве. Для публичных документов без строки в qrels нулевая оценка уже определена README. |
| Итоговый балл | Веса метрик, способ объединения результатов, формулы и размеры штрафов за скорость и модели. |
| Нагрузка | Параллелизм, длительность и число запросов, сценарий их подачи, распределение по ящикам, таймауты и учёт ошибок. |
| Прогрев и кеширование | Что разрешено кешировать, как прогревается сервис, включаются ли холодные запросы в измерение, каким способом рассчитывается p99. |
| Исполнение проверки | Способ запуска решения организаторами, доступное окружение и оборудование, доступ к сети, подготовка индексов и загрузка моделей перед проверкой. |
| Сдача выдачи | Точный формат файла или интерфейса и глубина выдачи для итоговой проверки. Входной публичный формат уже задаёт `query_id`, `synthetic_user` и `query_date`; официальный выходной формат пока не приложен. |
| Модельные ограничения | Как организаторы трактуют пограничные случаи использования моделей, в том числе предобработку запросов и офлайн-подготовку поисковых представлений. |
| Дополнительные баллы | Критерии бонусного трека и условия проверки доступности публичного сервиса. |
