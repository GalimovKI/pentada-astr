# Протокол

Контроли — штатный BM25 с учётом статуса и архивный BM25 с бонусом близости. Общий eval, K=1/5/10/20/50/100. Выбор на разработческой части по nDCG@10, затем Recall@10, MRR@10 и задержке. Проверка один раз на отложенных ящиках и на публичных 99 запросах. Для независимой диагностики строим воспроизводимую слабую разметку по явно запрошенной фразе и периоду, включая контрольные запросы без периода. Не используем эталонные границы при поиске.

После разработческой части (190 запросов, по трём вариантам nDCG@10 = 0,6126) проверяем обратный порядок дат и глагола получения и нечёткое ранжирование по дням для интервалов до восьми дней. Независимый диагностический срез из 67 пересекающихся интервалов строится только из полностью покрытых исходными оценками организаторов дней. Финальный выбор по nDCG@10 на разработческой части, контрольные пять ящиков до выбора не открываем.

## Итоги цикла

В эксперименте `20261121T225146Z-c3396be4` отбор по дате получения улучшил первую десятку на запросах с диапазоном. Например, для запроса «Найди письма с электронными чеками, полученные с 08.10.2028 по 09.10.2028» оба исходных движка пропустили все 12 релевантных чеков в первой десятке. Обе новые конфигурации вернули десять релевантных чеков.

## Что сравнивали

Контролями служили штатный BM25 с учётом статуса (`event`) и BM25 с бонусом близости слов (`proximity`). Второй воспроизводит реализацию из командной записи `20261121T203640Z-a8bbe625`, где он лидировал на 60 контрольных запросах. Сами 60 запросов и их парная разметка доступны в локальном checkout автора того исследования. Ниже приведены только сравнения на наборах, доступных для нового прогона.

Парсер распознаёт явные числовые и текстовые интервалы, последние N дней, предыдущую и текущую календарную неделю или месяц. Он связывает период со словами о получении, отсчитывает относительные даты от даты сценария и сохраняет тематическую часть запроса для BM25. Для строгого периода нужны известная дата письма и совпадающий ящик. При отсутствии распознанного периода работает штатный поиск.

Первая серия проверила три способа учесть период. Поздний фильтр (`late`) отбирает подходящие письма из первых 100, ранний (`early`) учитывает период во всём ящике, мягкий (`soft`) умножает балл за его пределами на 0,4. На 190 разработческих запросах все три получили 0,6126 nDCG@10 против 0,4864 у лучшего контроля. На 67 объединённых запросах поздний фильтр дал 0,8768, мягкий вариант — 0,9232.

Во второй серии обе конфигурации дополнительно распознавали формулировку «с … по … пришло». Вариант `early-v2` ранжирует BM25 внутри всего интервала. Вариант `daily` в интервалах до восьми дней включительно применяет нечёткий поиск с учётом статуса отдельно по дням и объединяет результаты по баллам на общей статистике ящика. Для более длинного периода используется `early-v2`. Для отложенной проверки заранее выбран `daily` по nDCG@10 на разработческой части.

## Задержка

Последовательный вызов движка в одном процессе на Apple M1 Pro, CPU. После построения индекса один проход по 136 запросам прогрел кеш. Затем выполнены пять проходов в перемешанном порядке, одинаковом для всех вариантов, по 680 вызовов с K=100 на движок. Измерение исключает сеть, очередь, PostgreSQL и построение индекса.

|---|---:|---:|---:|

## Границы проверки

- Для диагностики использован исходный корпус из 16 376 писем. Семь ящиков, представленных в публичных запросах, использованы для разработки. Остальные пять целиком отложены. Фразы детерминированно выбраны из текстов писем, а бинарные оценки построены по буквальному вхождению фразы и календарю. В обеих частях есть запросы без периода. Формулировки шаблонные.
- 67 интервалов сохраняют тему исходных запросов организаторов. Для каждого интервала подтверждены эталоны по всем дням, в которые в ящик поступали письма. Оценки объединены без ручного добавления положительных примеров. Интервалы пересекаются, а формулировки происходят из публичной части. При таком числе эталонов максимально достижимый Recall@10 равен 0,6490. Нечёткий вариант достиг этого потолка.
- На публичной части потолок Recall@10 равен 0,9376. У действующего движка остались два запроса с неполным nDCG@10. Наибольшая потеря — порядок трёх писем о завершении досмотра контейнеров, nDCG@10 0,7929. Эксперимент с периодами эту ошибку не исправил.
- Результаты описывают поддержанные русские формулировки. Качество на закрытых запросах организаторов неизвестно. Случаи, когда пользователь указывает только дату доставки или оплаты, дополнительно проверены модульными тестами.

## Воспроизведение

Из корня исследовательской ветки, с архивом организаторов в стандартном каталоге, выполните команды ниже. Общий eval использует K = 1, 5, 10, 20, 50, 100, делает один поиск до 100 и валидирует ящик и доступность каждого результата. Индексы строятся только по документам. Каждая команда записи ожидает новый выходной каталог.

```bash
uv sync --project backend --locked
export PYTHON="$PWD/backend/.venv/bin/python"
export PYTHONPATH=backend/src
archive=data/raw/mipt_mail_search_participants.zip
data=data/benchmarks/receipt-period-v1
out=reports/quality/runs/receipt-v1
"$PYTHON" experiments/receipt-period/build_probe.py "$archive" "$data"
"$PYTHON" experiments/receipt-period/build_joined.py "$archive" "$data/joined"
bash experiments/receipt-period/run.sh "$data/development" "$out/development" event proximity late soft early early-v2 daily
bash experiments/receipt-period/run.sh "$data/joined" "$out/joined" event proximity late soft early-v2 daily
bash experiments/receipt-period/run.sh "$data/heldout" "$out/heldout" event proximity early-v2 daily
bash experiments/receipt-period/run.sh "$archive" "$out/public" event proximity early-v2 daily
for lang in ru en; do
    bash experiments/receipt-period/run.sh "data/benchmarks/enronqa-ru/enronqa-$lang-$lang.zip" "$out/enron-$lang" event daily
done
"$PYTHON" experiments/receipt-period/analyze.py "$archive" "$data" "$out" data/benchmarks/enronqa-ru
"$PYTHON" experiments/receipt-period/latency.py "$data/heldout"
```

Сверены сохранённые выдачи и метрики всех 25 прогонов. Первые пять разработческих запусков выполнены до фиксации исходников в 55fa89e. Остальные использовали реализацию f6e91b9. Исходные поля git_dirty и hash сохранены в run.json каждого запуска. В некоторых прогонах рабочее дерево содержало новый аналитический скрипт. Итоговая ветка codex/receipt-period-research, коммит 12ebbd0. Backend-тесты с дополнением minilm обнаружили 84 теста, из них прошли 59 и пропущены 25.
