# Локальный eval и первый бейзлайн

Eval проверяет корректность данных и выдачи, рассчитывает метрики и сохраняет результаты для сравнения движков. Python-проект находится в `backend/` и работает на Python 3.11+. Пакет и закреплённую версию Snowball устанавливает `uv`.

## 1. Подготовка и запуск

Поместить предоставленный архив в `data/raw/mipt_mail_search_participants.zip`. Эта папка исключена из Git. Вместо копирования можно передать `--dataset /путь/к/архиву.zip` или путь к распакованной папке с пятью исходными файлами.

```bash
uv sync --project backend --locked
uv run --project backend --locked python -m unittest discover -s backend/tests -t backend -v
uv run --project backend --locked mailsearch validate
uv run --project backend --locked mailsearch run --output reports/quality/runs/bm25-reproduction
```

Команда `validate` проверяет manifest, SHA-256, количество строк, поля, даты, идентификаторы, ссылки разметки, ящики и доступность релевантных писем на дату запроса. Она печатает JSON со статистикой и fingerprint данных. ZIP читается напрямую без распаковки.

Команда `run` загружает проверенный набор, строит движок по корпусу и выполняет все запросы. Параметры BM25 по умолчанию совпадают с `configs/search/bm25.json`; этот файл можно передать явно:

```bash
uv run --project backend --locked mailsearch run --config configs/search/bm25.json --output reports/quality/runs/bm25-explicit-config
```

Каждый прогон сохраняется в новую папку: существующие результаты не перезаписываются. Папки прогонов `reports/quality/runs/` исключены из Git; короткие сводки `reports/quality/*.md` коммитятся. Сводка первого выполненного прогона сохранена отдельно в [reports/quality/baseline.md](reports/quality/baseline.md).

Для сравнения запусти BM25 со стеммингом через тот же eval:

```bash
uv run --project backend --locked mailsearch run --config configs/search/bm25-stemmed.json --output reports/quality/runs/bm25-stemmed
uv run --project backend --locked mailsearch compare reports/quality/runs/bm25-reproduction reports/quality/runs/bm25-stemmed
```

## 2. Метрики и правила локальной оценки

Значения K по умолчанию: **1, 5, 10, 20, 50, 100**. Их можно задать через `--ks 5 10 20`. Движок получает максимальное K один раз для каждого запроса; метрики меньших K рассчитываются по префиксам одной выдачи.

- **Recall@K:** найденные релевантные письма / все релевантные письма запроса.
- **nDCG@K:** бинарный DCG с дисконтом `1 / log2(rank + 1)`, делённый на идеальный DCG для этого запроса и K. Ранг начинается с 1.
- **MRR@K:** обратный ранг первого релевантного письма в первых K результатах; 0 при отсутствии такого письма.
- **MRR@K single:** отдельное среднее только по запросам с одним релевантным письмом — 42 запроса в текущем наборе, согласно рекомендации README организаторов.

Основные метрики макроусредняются по всем запросам. Документ без строки qrels для данного запроса получает оценку 0. Для запроса без релевантных документов все три метрики равны 0; такие запросы остаются в среднем. В публичном наборе запросов без релевантных документов нет. Прогон с ошибками движка сохраняет эти запросы в среднем с нулевыми метриками и явно отмечает ошибки.

Эти K, усреднение и поведение для запросов без релевантных документов — явные локальные настройки. Официальные K, веса и способ объединения метрик ещё не предоставлены. Итоговый балл хакатона инструмент не вычисляет.

## 3. Проверки выдачи и результаты запуска

Eval проверяет, что:

- представлен каждый входной `query_id`, без лишних запросов и повторов;
- каждый `doc_id` существует и встречается в выдаче запроса один раз;
- документы принадлежат ящику запроса;
- документы с известной датой получения после `query_date` не возвращаются;
- движок возвращает не больше запрошенного K и конечные числовые оценки.

Порядок движка сохраняется без повторного ранжирования в eval. Соответствие смыслу и запрошенному периоду оценивается по qrels; eval не заменяет разметку собственной интерпретацией текста.

| Файл прогона | Содержимое |
| --- | --- |
| `run.json` | Статус, движок, фактическая конфигурация, версии Python/платформы, SHA-256 всех вложенных Python-модулей пакета и внешнего файла фабрики движка, Git commit и dirty-флаг, fingerprint и контрольные суммы данных, время построения и вызовов движка. |
| `metrics.json` | Агрегированные метрики для каждого K, число запросов, ошибок и запросов с одним релевантным документом. |
| `predictions.jsonl` | Сохранённая выдача в локальном формате `query_id` → `doc_ids`. |
| `per_query.jsonl` | Запрос, ящик, дата, метрики по K, релевантные и пропущенные документы, время вызова и ошибка при наличии. |
| `report.md` | Читаемая сводка с метриками, временем и десятью запросами с наименьшим nDCG@10; если K = 10 не задано, используется максимальное K. |

Коды завершения: **0** — успешный запуск; **1** — прогон завершён с ошибками отдельных запросов, отчёт сохранён; **2** — ошибка данных, входной выдачи, конфигурации или запуска команды. Ошибочный ответ движка не учитывается как корректная выдача, но запрос не исчезает из знаменателя метрик.

## 4. Повторная оценка выдачи и сравнение

Локальный формат `predictions.jsonl`:

```json
{"query_id": "H-example", "doc_ids": ["L-first", "L-second"]}
```

`doc_ids` перечисляются по убыванию релевантности. Для запроса без результатов нужна запись с пустым списком. Это внутренний формат инструмента; официальный формат финальной сдачи ещё требуется получить.

```bash
uv run --project backend --locked mailsearch score --predictions reports/quality/runs/bm25-reproduction/predictions.jsonl --output reports/quality/runs/bm25-rescored
uv run --project backend --locked mailsearch compare reports/quality/runs/bm25-reproduction reports/quality/runs/bm25-rescored
```

Команда `score` позволяет оценивать сохранённые результаты любого движка без повторного поиска. Для внешней выдачи задержка поиска не измеряется. Некорректная или неполная внешняя выдача отклоняется.

`compare` показывает разницу метрик между двумя прогонами и число ошибок. Сравнение разных fingerprint данных, наборов K или правил усреднения отклоняется.

## 5. Подключение следующего движка

Движок реализует интерфейс из `backend/src/mail_search/domain/models.py`:

```python
def create_engine(documents: tuple[Document, ...], config: dict) -> SearchEngine:
    ...

# Метод возвращённого объекта:
def search(self, request: SearchRequest, k: int) -> list[SearchHit]:
    ...
```

Фабрика получает только документы и конфигурацию, без qrels и списка запросов. `SearchRequest` содержит `query`, `synthetic_user` и `query_date`; идентификатор запроса и разметка в него не входят. `SearchHit` содержит `doc_id` и числовой `score`. Порядок результатов определяет движок.

```bash
uv run --project backend --locked mailsearch run --engine mail_search.search.my_engine:create_engine --config configs/search/my_engine.json --output reports/quality/runs/my-engine-v1
```

Фильтры ящика и доступности по дате должны применяться внутри движка. Eval проверяет результат и сообщает об ошибке, если нарушены ограничения; он не исправляет выдачу молча. Тот же интерфейс можно использовать из будущего backend/API.

## 6. Что входит в первый BM25-бейзлайн

- Unicode NFKC, приведение регистра, `ё` → `е`, разбиение на буквенно-цифровые токены. Морфологии, стемминга, словаря синонимов, embeddings и reranking пока нет.
- Инвертированный индекс и BM25 отдельно для каждого ящика: `k1 = 1.2`, `b = 0.75`, положительный IDF `log(1 + (N - df + 0.5) / (df + 0.5))`. Статистика индекса строится по всему ящику один раз, фильтры доступности применяются при поиске.
- Простая интерпретация одного дня: «сегодня», «вчера», «позавчера», `YYYY-MM-DD` или русская дата вида «1 января 2025 года». Точка отсчёта — переданная `query_date`.
- Одиночное упоминание даты трактуется как целевой день получения. Диапазоны, несколько дат и сложные временные условия пока не разбираются. Наблюдение о предыдущем дне во всех публичных запросах не зашито как общее правило.
- Из запроса убирается распознанное выражение даты. Письма другого ящика, известные будущие письма и документы вне распознанного дня исключаются до отбора top-K.
- При распознанном дне `doc_dt = null` не подтверждает соответствие и исключается. Без ограничения на конкретный день неизвестная дата сохраняется допустимой. Это решение P08, а не дополнительно установленное правило организаторов.
- При одинаковых оценках порядок определяется `doc_id`. Документы без общих токенов с запросом не возвращаются; выдача может быть короче K.

Конфигурация `date_filter = false` отключает интерпретацию дня из текста, сохраняя обязательные фильтры ящика и доступности на `query_date`. Она предназначена для будущих сравнительных экспериментов; первый результат получен с `date_filter = true`.

В `configs/search/bm25-stemmed.json` настройки `stemming: true` и `date_mode: "contextual"` применяют Snowball к русским словам в письмах и запросах. Токены с цифрами и латиницей сохраняются после обычной нормализации. Явный день получения становится фильтром. Даты события остаются в тексте запроса. Некорректные даты и неоднозначные интервалы обрабатываются как текст. Запрос из одной относительной даты вроде «вчера» выдаёт письма нужного ящика за день. Команда `search` принимает ту же конфигурацию и возвращает упорядоченные `doc_id` с оценками. Пример запуска есть в [README.md](README.md).

## 7. Границы первого измерения

Время измеряется через `perf_counter_ns` вокруг вызова `search`, включая получение всех его результатов. Построение индекса, чтение корпуса, валидация выдачи и расчёт метрик вынесены за этот замер. Используется один последовательный проход, без отдельного прогрева и без кеширования выдачи в базовом движке. p50/p95/p99 рассчитываются методом nearest rank; при 99 запросах p99 равен максимальному наблюдению.

Это измерение движка в процессе, а не проверка серверного `p99 < 1 с`: backend, конкурентная нагрузка и официальный сценарий ещё не реализованы. Таймауты вызовов eval пока не прерывает. Результаты зависят от оборудования и отражены вместе с платформой в `run.json`.

Публичный набор содержит всего 99 запросов к 7 из 12 ящиков. Метрики на нём — исходная точка для экспериментов; они не подтверждают качество на приватном наборе. Улучшения следует сравнивать через этот же eval, сохраняя конфигурации и выдачу.

## 8. Размещение в структуре приложения

- `backend/src/mail_search/domain/` — общие модели и интерфейс движка.
- `ingestion/dataset.py` — загрузка официального архива и проверка manifest и разметки.
- `indexing/` — токенизация и построение индекса; `search/` — запросы, даты и BM25.
- `evaluation/` — проверка выдачи, метрики, отчёты и офлайн-прогон.
- `benchmarks/latency.py` — диагностические перцентили времени вызова движка.
- `core/` — ошибки, определение корня checkout и версия исходников; `cli.py` — команды.
- `backend/tests/unit/`, `backend/tests/integration/`, `backend/tests/fixtures/` — проверки и синтетические данные.

Конфигурации поиска находятся в `configs/search/`, короткие сводки — в `reports/quality/`. API и PostgreSQL подключаются к тому же пакету, когда начинается разработка приложения; для офлайн-eval база не требуется.

Команды выше выполняются из корня репозитория. Из каталога `backend/` можно использовать `uv run --locked mailsearch ...` и `uv run --locked python -m unittest discover -s tests -t . -v`. Путь архива по умолчанию определяется от checkout, независимо от текущего каталога; явно заданные относительные пути `--dataset`, `--config` и `--output` считаются от рабочего каталога команды.
