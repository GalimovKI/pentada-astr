## 2. Форматы исходных файлов

JSONL: один JSON-объект на строку. Ниже приведены исходные поля; это не проект внутренних моделей приложения или HTTP API.

### `documents.jsonl`

| Поле | Тип в предоставленном файле | Значение |
| --- | --- | --- |
| `doc_id` | string | Идентификатор письма, используемый в qrels и выдаче. В этой версии все идентификаторы уникальны во всём корпусе. |
| `synthetic_user` | string | Идентификатор синтетического почтового ящика. |
| `doc` | string | Полный доступный текст письма. Отдельных полей темы, отправителя, получателей, HTML, вложений или цепочки в схеме нет. |
| `doc_dt` | string или null | Дата получения в формате `YYYY-MM-DD`; null означает неизвестную дату. |

Структура текста `doc` неоднородна: только 988 писем начинаются с `Тема:`. Наличие отдельной темы или заголовков для каждого письма не гарантируется.

### `queries_dev.jsonl`

| Поле | Тип | Значение |
| --- | --- | --- |
| `query_id` | string | Уникальный идентификатор запроса. |
| `synthetic_user` | string | Ящик, в котором выполняется поиск. |
| `query` | string | Текст пользовательского запроса. |
| `query_date` | string | Дата запроса в формате `YYYY-MM-DD`, точка отсчёта относительных периодов. |

Идентичный текст может встречаться у разных запросов с разными датами. В наборе 99 записей и 85 уникальных текстов запросов.

### `qrels_dev.jsonl`

| Поле | Тип | Значение |
| --- | --- | --- |
| `query_id` | string | Ссылка на запрос из `queries_dev.jsonl`. |
| `doc_id` | string | Ссылка на письмо из `documents.jsonl`. |
| `relevance` | integer | В этой версии всегда 1: документ релевантен запросу. |

Для расчёта публичных метрик отсутствие пары `(query_id, doc_id)` в таблице означает оценку 0, согласно README. Это правило оценки по публичной разметке, а не утверждение о полноте семантической разметки всех писем.

## 3. Правила выполнения запросов из README организаторов

1. Каждый запрос выполняется в ящике из его поля `synthetic_user`.
2. Относительные периоды интерпретируются относительно `query_date`. Например, при `query_date = 2025-10-20` слово «вчера» означает 2025-10-19.
3. Письмо с известной датой получения после даты запроса ещё недоступно: `doc_dt > query_date` исключает его из поиска. Само по себе равенство дат не делает письмо будущим.
4. `doc_dt = null` означает неизвестную дату, а не дату запроса или минимальную дату.
5. Для локальной проверки README предлагает Recall@K и nDCG@K по публичной таблице. MRR@K для поиска конкретного письма предлагается считать по запросам с одним релевантным документом.
6. Объекты без строки релевантности для данного запроса получают оценку 0 при расчёте метрик. Итоговый замер выполняется организаторами на закрытом бенчмарке.
7. README повторяет требование к p99 бэкенда: строго менее 1 секунды.

README не устанавливает значения K, веса итоговой оценки, окончательные правила усреднения или полный нагрузочный протокол. Также не определена полностью обработка писем с неизвестной датой при поиске за конкретный период. Эти вопросы остаются открытыми в PROJECT.md.

## 6. Следствия для реализации

- **C01/C03:** сохранять `synthetic_user` и `doc_dt` вместе с исходным `doc_id`; проверять manifest; поддерживать неизвестную дату без её подмены.
- **C04:** принимать текст, ящик и дату запроса. Разделять доступность письма на дату запроса и соответствие периоду, указанному в тексте запроса. Семантическое ранжирование выполняется в корректном контексте.
- **C04/C07:** при использовании кеша учитывать ящик и дату вместе с запросом и версией поисковой конфигурации. Повторяющийся текст не означает идентичный поиск.
- **C05:** читать публичные JSONL напрямую через входной адаптер, применять бинарную разметку и явно указывать K и набор запросов для каждой метрики. Официальный выходной формат сдачи ещё требуется получить.
- **C07/C08:** передавать дату сценария явно и дать пользователю демо возможность её задать; для бенчмарка брать исходную `query_date` без изменения.
- **C09:** привязывать запуск к версии архива или контрольным суммам файлов и к параметрам обработки дат. Поддерживать все 12 ящиков, включая пять без публичных запросов.

Данные подтверждают необходимость временной фильтрации, но сами по себе не фиксируют стек, алгоритм поиска, модель или обязательность reranking. Выбор следующего технического решения должен опираться на измерения качества и скорости.
